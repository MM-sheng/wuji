# keeper RPC 恢复修复 · 2026-10-22

用户要求按规划排查并修复后台偶发 RPC 错误。本轮修改链下读取、故障计数和运行快照，
不修改合约、费率、指数公式、确认深度、签名账户或签名预算。

## 已确认的问题与边界

历史日志存在 `accounts: <pool> RPC eth_call failed after 3 attempt(s): fetch failed`。
旧的 `maintainAccounts` 逐池捕获错误后不向主循环报告；主循环只按 `round()` 失败计数，
成功读取指数就清零。因此即使某个池的维护持续网络失败，也不会触发既有的监督重启。
故障注入复现了“头链一直正常、池 A 一直 ECONNRESET、池 B 正常”的场景。

旧日志没有保留底层网络 cause，不能断言历史故障源自服务商、代理、DNS 或连接池。
本轮没有在实际签名服务上注入故障，也不声称以后互联网不会断线。

## 修复

- RPC 有界重试预算保持不变；网络失败额外携带 `rpcTransportError` 分类。
  错误日志只保留 HTTP 状态、标准网络错误码和 Timeout/Abort/Syntax 类型，
  不输出嵌套异常文本、RPC URL、请求参数或凭据。支持 AggregateError 的嵌套 cause。
- 新 `keeper-health.mjs` 独立统计指数轮次失败与每个池的连续网络失败。
  其他池成功、指数正常等待都不能清掉坏池的计数；该池网络恢复后才清零。
  正常合约回滚、HTTP 401 等非暂态客户端错误不算连接恢复触发条件。
- `maintainAccounts` 继续检查其余池，完成整轮后返回各池网络结果；达到阈值再退出，
  由原 launchd KeepAlive 机制重启。现有部署阈值仍为 3 轮，间隔仍为 120 秒。
  不在有正在等待的维护调用时主动截断该调用；不新增交易发送重试。
- 可选状态读取发生网络错误时向上报错，不能把 settling/insolvent/frozen 等当成 false，
  也不能把 nextPricingHeight/claimable 等当成不存在。旧合约缺少可选接口的回滚兼容行为保留。
  指数可选能力读取同样不能把网络故障缓存为 verifier=0 等默认值；非暂态 HTTP 读取错误
  也会阻止可选字段读取，但不计入逐池网络重启计数。

JSON-RPC 执行错误仍直接返回；非白名单方法（包括交易提交）仍只尝试一次。
旧 `cast` 仿真/发送错误路径未改为自动重试；本轮不等同于为所有外部进程错误建立统一分类。
