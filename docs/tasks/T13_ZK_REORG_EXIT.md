# T13 · 无中继指数的主网规则：三条规则，无人值守

2026-10-02 · 状态：**已实现并部署到 Sepolia（未审阅）**：`contracts/deployments/sepolia-t13.json`；项目方确认 K = 100、池子定价改为单一规则（见末节"实现记录"）。适用于主网采用的"只走区块头路径的 `ZkWujiIndex`"
（[区块头路径优先决策](../decisions/2026-10-02-header-path-first.md)）。取代本文件 2026-10-02 早些时候的"通知 / 取消 / 等待"版本，
那一版要求有人按时在线取消假通知，不符合"无人维护也能运行"的目标。

## 目标

和比特币一样：**规则只有几条，全部由数学和比特币算力保证，不需要任何人按时在线盯着。**
唯一去不掉的假设是：至少有一个人把公开的比特币区块头提交上链（任何人都能做、有赏金、无法造假，见 §5）。

## 三条规则

### 规则 1：区块头必须合法

PoW 不超过目标值、哈希首尾相连、难度等于父块或按 2016 块重定向（×4/÷4 上下限）、时间高于前 11 块中位数、
不超前当前时间 2 小时。已实现（`_apply`），与 Rust guest 和 JavaScript 实现做过差分测试。

### 规则 2：只计入足够深的区块

`foldHeaders` 只把**后面还跟着 K 个合法区块**的高度计入指数（现在是 `CONFIRMATIONS = 6`，改为构造参数 `K`）。
安全性就是比特币自己的确认数学（中本聪白皮书 §11）：攻击者想让指数走上自己私挖的分支，必须在诚实链产生 K 个块之前，
先挖出 K+1 个块。成功概率（q = 攻击者占全网算力的比例）：

| K | q = 10% | q = 20% | q = 30% | q = 40% |
|---:|---:|---:|---:|---:|
| 6 | 2.4e-4 | 1.4e-2 | 0.13 | 0.50 |
| 12 | 8.9e-8 | 2.9e-4 | 2.4e-2 | 0.31 |
| **24（建议）** | 1.3e-14 | 1.4e-7 | 8.1e-4 | 0.12 |
| 36 | 1.9e-16 | 6.4e-11 | 2.9e-5 | 4.9e-2 |

代价：指数晚 K 个块生效（K = 24 约 4 小时）。T11 池子的 A 定价按已终结链尾年龄计算，会相应变慢（§6）。

### 规则 3：深度重组就封存

任何人可调用 `freezeOnReorg(baseHeight, baseState, headers)`，满足以下全部条件时，指数**立即、永久**封存：

1. `baseState` 是一次已记录的推进终点：`committedAt[baseHeight] == keccak(baseState)`，且 `baseHeight < 链尾高度`。
2. `headers` 从 `baseState` 起按规则 1 全部合法。
3. 这条分支**不经过**当前已终结链尾（在链尾高度处哈希不同）。
4. 分支工作量 ≥ 已终结链的工作量 + **(K + D)** 个块的工作量（以链尾难度计）。**D = 144**。

没有通知、取消或倒计时：等待已经折算进第 4 条的工作量门槛里。

- **真的深重组**：新链就是全网最重的链，从分叉点起再长出 K + D 个块（约 1 天），任何人提交即可封存。
- **伪造封存**：攻击者要私挖一条比已终结链再重 K + D 个块（约 170 个）的分支，而且要赶在诚实链把指数推进之前，代价极高。
- 封存后，`S`、检查点、`lastHeight`、`lastHash` 定格在最后一次推进的状态；所有推进入口永久拒绝。
  T11 池子用现有的 `freezePool` 退出：已标记的定价高度按各自的 S 结算，其余按封存时的 S 结算，定价晚于封存高度的入场全额退款。

**为什么封存、而不是跟随新链**：已按旧链结算并支付出去的钱收不回来，跟随新链会造成重复支付或资金缺口（同 T9 §3）。

## 需要新增的状态

| 状态 | 作用 | 代价 |
|---|---|---|
| `committedAt[height]` | 每次推进后记一笔已终结状态的哈希承诺，作为规则 3 的合法分叉起点 | 每次推进 +1 存储槽 ≈ 22k gas（每 6 小时推进一次约 +3%） |
| `frozen` | 封存标志，接口同 `WujiIndex.frozen()`，池子据此启用冻结退出 | 1 槽 |
| `K`（immutable） | 规则 2 的确认深度，取代常量 `CONFIRMATIONS` | 无 |

只存承诺，不存完整状态：调用者在 calldata 里给出完整的旧状态，合约核对哈希后才使用。

## 主网上**不需要**的东西

ZK 证明、挑战窗口、挂起队列、争议和保证金、`back` / `reject` / `refute`、watcher、重组通知。
主网部署时 `verifier = address(0)`、挑战参数为零，这些入口全部不可用（构造函数已支持）。
这部分代码和测试保留，在测试网上作为研究成果和将来的选项（T10、T12）。

## 剩下的假设，明确写出

1. **至少有一个人提交区块头。** 合约看不到比特币网络。任何人都能提交，有手续费储备付赏金（`RelayerRewards`），
   区块头造不了假。无人提交时指数暂停、不会算错。
2. **诚实提交要及时。** 规则 2 的概率表假设诚实链能及时送进来、攻击者需要赛跑。如果很长时间只有攻击者在提交，
   他可以从容私挖 K+1 个块让指数走上自己的分支；真实链随后送进来时，规则 3 触发封存，攻击者付出了约 K+1 个块的挖矿成本，
   换来指数在那段时间里走在他的分支上。赏金越可靠，这段空窗越短。
3. **比特币本身。** 攻击者算力过半时，以上全部失效，比特币也一样。
4. **D = 144 与 K = 24 是候选值**，没有经过经济论证；主网前与敞口政策一起审阅。

## 实现边界与开销

- 规则 3 的一次提交要包含：分叉起点到链尾的原链长度（最多一次推进的长度，≤ 506）加上 K + D（168）个块，
  最坏约 674 个区块头，约 12.6M gas，在单笔交易 16.7M 的上限内。规则 3 的单笔区块头上限设为 800。
  建议 keeper 每次推进不超过约 250 个高度，让这个最坏情况保持宽裕。
- 规则 3 没有赏金：调用者自己付 gas。真深重组时，持有资产的人有足够动机去调用。

## 对 T11 池子的影响

- A 定价的"年龄"是 `现在 − 已终结链尾时间`。K = 24 时，链尾刚推进完就已约 4 小时旧，再加上推进间隔：
  每 6 小时推进一次，年龄约 4–10 小时，A 的等待约 13–18 小时。
- B（申请人提交区块头）不受推进间隔影响，约 7 小时 + K 带来的延迟。
- 如果主网追求最少的规则，可以只保留 A，去掉 B。

## 测试计划

真实难度的分叉没法在测试里挖出来，沿用 T9 的做法：**只在测试中使用的低难度子合约**（放宽 PoW 上限，规则代码共用），真挖分叉。生产合约不加低难度模式。

1. 规则 2：推进只计入后面跟着 K 个区块的高度；K 由构造参数决定。
2. 规则 3 不触发：浅分叉（不越过链尾）、经过链尾的同一条链、工作量差一个块、分叉起点没有承诺记录、起点状态与承诺不符。
3. 规则 3 触发：工作量恰好达到门槛时封存；封存不可逆，之后 `foldHeaders` 等全部拒绝。
4. T11 池子在封存后 `freezePool` 正确结算与退款（复用现有池子测试的断言）。
5. 不变量：任意调用序列下 `frozen` 一旦为真永不变假；未封存时 `S` 只经规则 2 改变；`committedAt` 只追加不修改。

## 构建顺序

1. 合约：`K` 改为构造参数，增加 `committedAt`、`freezeOnReorg`、`frozen`；补测试与不变量。
2. keeper：限制单次推进的高度数（≈ 250）；终端显示封存状态。
3. 测试网部署，与 WUJI-14 的修复一起。
4. 交独立审阅（主网前）。

## 实现记录（2026-10-02）

项目方确认：**K = 100**（比特币自己的 coinbase 成熟期），永续池定价合并为一条规则。

- `ZkWujiIndex`：`CONFIRMATIONS` 改为构造参数（`Schedule{genesisHeight, checkpointInterval, confirmations}`），
  每次推进写 `committedAt[height]`，`seenHeight`/`seenTime` 记录验证过的最新区块头（含未满 K 的尾部），
  新增 `freezeOnReorg(base, headers)` 与 `frozen`；封存后 `foldHeaders`、`foldProof`、`finalize`、`dispute`、
  `refute` 一律拒绝。去掉了 `seenTip` 与 `lastTime`。
- `WujiAccounts`（无中继模式）：定价 = `seenHeight + 按 seenTime 年龄查表的余量`，`seenTime` 超过 24 小时拒绝；
  去掉了原来的 A（按已终结链尾）和 B（申请人提交区块头）。`frozen()` 存在，所以池子可以走冻结退出。
- keeper：合约没有验证器时直接走区块头路径，凑够 `K + 36` 个区块头就推进，单次最多推进 250 个高度；
  所有交易的 gas 上限都控制在 16M 以内（EIP-7825）。顺带修复：原来的回退路径把 gas 上限设成了 60M，会被 RPC 直接拒绝。
- 测试：`test/ZkWujiReorg.t.sol` 用只在测试中存在的低难度子合约真挖分叉，覆盖：工作量恰好达到门槛才封存（另有 256 轮随机测试）、
  经过已终结链尾的链不算、只能从有记录的状态分叉、封存后不能再推进、池子封存后全额退款。Foundry 227 个全部通过。
- anvil 实测：K = 100、只走区块头路径的合约，keeper 一笔提交 350 个区块头、推进 250 个高度，634 万 gas；
  `seenHeight` 比已终结高度多 100；S 与独立重算一致。
